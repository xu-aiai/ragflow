## 0. 设计思路与核心原则

> 本章是全文的"为什么"。§2~§5 的格式定义只是本章推理的结果——**评审时先批这里**。

### 0.1 要解决的问题

三本 Word 手册（操作/维修/EU 操保）要变成车机上的随车助手：能翻（手册）、能问（问答）、能查故障（输码 + 诊断）、能提醒保养。**直接在车机上解析 Word 不可行**：嵌入式硬件、必须离线、Word 格式千变万化、源文件还有 DRM 透明加密。整个设计围绕一件事：**把 Word 的复杂度一次性消灭在管线侧，车机只消费即读即渲染的成品数据**。

### 0.2 八个关键决策与理由

| # | 决策 | 为什么 | 否决的替代方案 |
|---|---|---|---|
| 1 | **厚数据、薄运行时**：管线一次性抽取，车机只做"读 JSON → 渲染" | Word 解析复杂度（自动编号/合并单元格/矢量图/DRM）绝不能上车；车机离线、资源有限 | 车机直接渲染 docx/PDF——嵌入式没有像样的渲染器，且无法深链、按变体过滤、局部更新 |
| 2 | **丢表现层、留语义层**：字体/字号/颜色丢弃；结构、强调、引用保留 | "格式不乱"的唯一保证 = 车机只渲染认识的封闭块集，样式由 App 设计系统接管 | 初版"丢掉 Word 的皮"执行过头——加粗/超链接也被当皮肤扔了（A 手册实测 769 处加粗、160 个链接被静默拍平）；DITA 官方哲学：`b`/`xref` 是语义不是皮肤，已修正 |
| 3 | **结构化与语料分离，一事实一权威**：查表/规则给程序算，散文给 LLM 查 | 查码要精确不要相似；同一事实存两处必然漂移；规则要执行不能被检索 | 全塞知识库走 RAG——行业对标：四大诊断工具全是确定性引擎 + LLM 访问层，无厂商用纯 RAG |
| 4 | **标准先行**：字段名/含义照搬 DITA/RWPM/J1939/OTX，JSON 只是载体 | 自造字段要永久维护映射表（税）；标准是行业验证过的模型；对接外部系统有机械转译逃生门 | 自造格式 + 映射表——每个字段都要重新论证，映射永远追不上变更 |
| 5 | **规范先行、产品为视图**：本规范是地基，随车助手/手册库是应用 | 产品会迭代（车机 → Web → 平台），规范不能跟着产品变；新产品 = 加视图，新机型 = 重跑管线 | 按产品定义数据格式——每个新产品改一次格式，格式永远不稳定 |
| 6 | **封闭集 = 标准的约束剖面**：词汇表按证据裁剪（DITA 官方 constraints 机制），准入三条（§2.2） | 封闭集是渲染保证（每元素一个 delegate）；DITA 全集 140+ 元素 vs 实测所需约 15，10 倍工作量换 0 价值；审核清单是安全的发现机制 | 全量对齐 DITA——为不存在的用例维护上百个 delegate；也否决"随意自造"——**子集内的语义必须逐字对齐标准** |
| 7 | **稳定 ID，章节号只是显示锚** | 改版重编号（2.5.1→2.6.1）不能断深链；行业实践一致（EPUB URN / DITA key / S1000D DMC） | 含章节号的 ID——每次改版全部引用重写 |
| 8 | **派生物可随时重建**：RAGChunk/SearchRecord/OfflinePackage 从权威数据派生 | 权威只有一份，其余坏了重建；防止派生物变成第二权威后漂移 | 派生物独立维护——必然与权威失同步 |

### 0.3 核心原则（上述决策的浓缩）

1. **标准优先**：能用行业标准字段（名字与含义）就不自造；JSON 只是载体语法，不自造字段、不维护映射表（§1）。
2. **规范内容是唯一权威**：搜索索引、RAG 语料、终端页面、离线包全部是派生物，可随时重建；权威数据只有一份。
3. **原件不可变，Edition 不可变**：修改内容必须产生新 Edition；已发布 Edition 永不就地修改。
4. **标识稳定**：ID 不含章节号、标题等会随版本变化的信息——行业标准的共同实践（EPUB 用 URN、DITA 用 key、S1000D 用 DMC 码，无一例外）。
5. **确定性优先**：确定性功能（查码、规则求值）不使用相似度猜测；类型封闭，无法归类的内容进审核清单，绝不透传。
6. **一事实一权威**：一条事实只存一处；能查表回答的走实体 + 工具调用，需要理解文字的走语料检索。

### 0.4 推理链

```text
Word 手册无法上车（DRM/格式/离线）
  → 复杂度消灭在管线侧（决策 1）
    → 车机只渲染封闭块集 → 块集语义必须对齐标准 → DITA 约束剖面（决策 2/4/6）
      → 同一内容两种消费（人读/程序算）→ 三子模型 + 一事实一权威（决策 3）
        → 产品会变、规范不变 → 规范先行、产品为视图（决策 5）
          → 改版不断链 → 稳定 ID（决策 7）；派生物可重建（决策 8）
```

先读本章（为什么）→ §1 标准地图（采用什么标准、不采用什么）→ §2~§5 格式定义（每种数据：标准如何做 → 我们如何参照实现 → 大而全示例 → 逐字段说明）→ §3.3~§3.5（物理布局与存储去向）→ §7 领域模型总图 → §9 应用如何消费。

## 1. 行业标准地图与采用决策

| 层 | 行业标准 | 官方形态 | 本规范采用方式 |
|---|---|---|---|
| 内容模型 | DITA 1.3+（OASIS） | XML | 全量采用其元素名/属性名/标准值，JSON 绑定（§1.1）→ §2 |
| 诊断内容形态 | DITA troubleshooting topic | XML | 同上 → §4.3 |
| 测试序列 | **ISO 13209 OTX**（Open Test sequence eXchange format；现行版 **ISO 13209-2:2022**） | XML | 采用其**语义子集**（原因分支 + 顺序步骤 + 通过判据 + 验证闭环），JSON 绑定 → §4.3 |
| 故障码身份 | SAE J1939 SPN/FMI、SAE J2012 | 协议 | 身份字段对齐（`spn`/`fmi`）→ §4.2 |
| 诊断通信 | SAE J1939-73（DM 消息族）、ASAM ODX | 协议 | **不实现**（车控域）；B4 信号映射与其对接 → §4.5 |
| 打包清单 | Readium Web Publication Manifest | **JSON（官方即 JSON）** | 原样采用 → §3 |
| 保养规则 | 无（SAP PM / Maximo 均为私有 schema） | — | 最小自造、诚实声明 → §5 |
| 更新安全 | TUF / Uptane | 签名元数据 | 平台期增强，预留接口不实现 |

**官方出处**（本规范引用标准一律给出可核对坐标；2026-11-07 验证可达）：

- **DITA 1.3**（OASIS Standard，2015-12-17）：<https://docs.oasis-open.org/dita/dita/v1.3/> —— 本规范采用 **Part 2 Technical Content 版**（含机械任务域与排障元素）；正式引用用 `os/` 目录版本，勘误见 `errata02`。DITA 2.0 已成为 OASIS 正式标准（2025），本规范锚定 1.3+，引用一律指向 1.3；
- **Readium RWPM**：<https://readium.org/webpub-manifest/> —— 官方规范站，含 JSON Schema（`publication.schema.json`）可作打包校验；
- **ISO 13209-2:2022**（OTX 核心数据模型，第 2 版取代 2012 版）：官方目录页 <https://www.iso.org/standard/76976.html>（标题/范围免费），全文付费，**ISO Online Browsing Platform（OBP）可免费预览**；
- **SAE J1939 / J2012**：SAE 官方文本付费；公开入门可读 Kvaser 高层协议页（<https://kvaser.com/about-can/higher-layer-protocols/>）与 CAN 词典。

### 1.1 JSON 绑定规则（本规范唯一自造物）

DITA / OTX 官方无 JSON 形态。本规范**不发明字段**，只定义一条拼写规则：

- 每个元素序列化为一个对象，元素名放在 `el` 字段；
- 元素属性成为同名字段（`type`、`href`、`alt`…）；文本内容放 `text`；子元素按标准结构放约定字段（`items`、`image`、`sthead`…）。

由此本规范数据与标准 XML 是**同构**关系——转 XML 只是换拼写，不需要对照表。

### 1.2 扩展机制（标准自带的扩展点，不是自造）

- 内容单元：DITA `@props` → `props` 对象（章节号、面包屑等印刷产物）；
- 打包清单：RWPM 命名空间扩展 → `xcmg:` 前缀字段；
- **应用层字段一律不得进入基础格式**，只能走上述扩展点。

## 2. 内容模型：DITA 的实施剖面

### 2.1 DITA 标准如何做

- **topic 类型**：信息类型按"回答读者什么问题"划分（官方 archSpec §2.2.1.4 Information typing）。根类型 `topic`（一切类型由它特化）+ 标准开局包：`concept`（是什么）/ `task`（怎么做；机械行业严格版 Machinery Task 见 Part 2 §2.7.1.5）/ `reference`（查阅）/ `troubleshooting`（排障，DITA 1.3+，**既是独立 topic 类型也是可嵌入其他 topic 的域**）/ `glossentry`（术语条目，DITA 1.2+）。标准期望各行业在开局包之上**特化**自己的类型——本规范的约束剖面即此机制的正用；
- **body 块级元素**：`p`、`ul/ol/li`、`note`（`@type` 标准值：`caution`/`warning`/`danger`/`notice`/`tip`）、`fig`+`image`（`@href`/`@alt`）、`simpletable`（规整数据表，`sthead`/`strow`）、**`table`**（CALS 复杂表：`@morerows` 纵向合并、`@namest/@nameend` 横向合并——**合并单元格在标准里由 `table` 而非 `simpletable` 表达**）、task 骨架（`taskbody > prereq / context / steps / result / postreq`，`step > cmd + info`）；
- **行内元素**：`b`/`i`（highlighting 域——官方明确"样式表可改变呈现，勿依赖其视觉效果"，且"仅当无更语义化元素可用时使用"）、`xref`（行内引用——官方明确"引用图表时链接到 `<fig>` 元素本身"，建议优先 `keyref` 键引用）；
- **profiling**（按变体过滤同一份内容）：`@product`、`@audience`、`@props` + DITAVAL；
- **标识**：key / URN，稳定不变。

> 元素级出处（官方参考页，2026-11-07 逐页核实）：`b`/`i`/`xref`/`table`/`simpletable`/`note` 见 DITA 1.3 Part 1《Language Reference: Base edition》§3.2（`note` 见 §3.2.2.24）；task 骨架见 Part 2《Language Reference: Technical Content》`taskbody` 及其子元素；机械任务域（Machinery Task topic）见 Part 2 §2.7.1.5。

### 2.2 本规范的 Topic 格式（参照实现）

**约束剖面声明**：本规范的封闭块集 = DITA 1.3 Technical Content 的**约束剖面**（DITA 官方机制，§1）——已采用元素的命名/含义/属性值与标准逐字一致，词汇表按证据裁剪。

**大而全示例**（一个 task 类 topic，覆盖封闭集全部元素；根元素 `el` 即 DITA 特化类型名，不另设 class 字段）：

**混合内容绑定规则**：`p`/`note`/`li`/`cmd` 用 `text`（纯文本）或 `runs`（数组——字符串为纯文本，对象为行内元素）。

**块级封闭集**（未知 `el` 进审核清单；黄金断言：包内未知块数 = 0）：

| `el` | DITA 元素 | 语义 | 关键字段 |
|---|---|---|---|
| `p` | `<p>` | 段落 | `text` 或 `runs` |
| `note` | `<note>` | 安全警示 | `type` ∈ DITA 标准值：`caution`(注意) / `warning`(警告) / `danger`(危险) / `notice` / `tip` |
| `ul` / `ol` | `<ul>` / `<ol>` | 清单 | `items[]`：`li`（`text` 或 `runs`） |
| `steps` | task `<steps>` | 操作程序 | `items[]`：`step{cmd, info?}` |
| `prereq` / `context` / `result` / `postreq` | taskbody 子元素 | 任务骨架（前提/背景/结果/后续） | `body[]`：块序列 |
| `fig` | `<fig>` | 插图 | `id?`、`title`、`image{href, alt}` |
| `simpletable` | `<simpletable>` | 规整数据表（无合并） | `sthead[]`、`strow[][]` |
| `table` | `<table>`（CALS） | 复杂表（带合并单元格） | `cols`、`caption?`、`thead[][]`、`rows[][]`；单元格 `{text, rowspan?, colspan?}` |

**行内封闭集**（出现在 `runs` 数组中）：

| `el` | DITA 元素 | 语义 | 关键字段 |
|---|---|---|---|
| `b` / `i` | `<b>` / `<i>` | 语义强调（官方：勿依赖其视觉效果） | `text` |
| `xref` | `<xref>` | 行内引用 | `href`（Topic URN，可带 `#元素id` 片段）、`text` |

**字段详细说明**

Topic 级字段：

| 字段 | 类型 | 必填 | 含义 | DITA 对应 |
|---|---|---|---|---|
| `el` | string | ✓ | 根元素名 = topic 类型（`task`/`concept`/`reference`/`troubleshooting`） | 特化元素名 |
| `id` | URN | ✓ | 稳定标识，跨 Edition 不变（§2.3）；深链与跨引用的唯一锚 | `@id` + key |
| `title` | string | ✓ | 标题 | `<title>` |
| `product` | string | ✓ | 适用机型/配置（§6） | `@product` |
| `audience` | string | ✓ | 受众（§6） | `@audience` |
| `props` | object | ○ | 标准扩展点，承载 Word 印刷产物 | `@props` |
| `props.docCode` | string | ○ | 源手册代号（A/B/C） | 扩展 |
| `props.chapterNo` | string | ○ | 章节号——**显示锚，改版可变，禁止用作引用目标** | 扩展 |
| `props.seq` | int | ○ | 文档流顺序，排序/导航一律用它 | 扩展 |
| `props.breadcrumb` | string | ○ | 面包屑路径 | 扩展 |
| `body` | array | ✓ | 有序块序列 | `<body>`/`<taskbody>` |

块级公共字段：

| 字段 | 含义 |
|---|---|
| `el` | 块类型（封闭集成员） |
| `text` | 纯文本内容（与 `runs` 二选一） |
| `runs` | 混合内容数组：字符串 = 纯文本，对象 = 行内元素 |
| `src` | 可选；版面流元素序号（工作台点击溯源用，车机运行时忽略） |

块专有字段：

| 字段 | 所属块 | 含义 | DITA 对应 |
|---|---|---|---|
| `type` | `note` | 警示级别：`caution`(注意)/`warning`(警告)/`danger`(危险)/`notice`/`tip` | `@type` 标准值 |
| `id` | `fig` | 图内锚点，供 `xref` 片段（`…#fig-2-38`）引用 | `@id` |
| `title` | `fig` | 图号/图题 | `<title>` |
| `image.href` | `fig` | 图片包内相对路径 | `@href` |
| `image.alt` | `fig` | 替代文本（无障碍 + 检索） | `@alt` |
| `items` | `ul`/`ol`/`steps` | 子项列表（`li` 或 `step`） | — |
| `cmd` | `step` | 步骤指令（`text` 或 `runs`） | `<cmd>` |
| `info` | `step` | 可选；步骤附加说明（块序列） | `<info>` |
| `body` | `prereq`/`context`/`result`/`postreq` | 骨架段的块序列 | 元素内容 |
| `sthead`/`strow` | `simpletable` | 表头/数据行（字符串二维数组，无合并） | `<sthead>`/`<strow>` |
| `cols` | `table` | 列数 | `<tgroup @cols>` |
| `caption` | `table` | 可选；表题 | `<title>` |
| `thead`/`rows` | `table` | 表头/数据行（单元格对象二维数组） | `<thead>`/`<row>` |
| `rowspan` | `table` 单元格 | 纵向跨行**总数**（HTML 语义；DITA `@morerows` = rowspan − 1） | `@morerows` |
| `colspan` | `table` 单元格 | 横向跨列数 | `@namest/@nameend` 简化绑定 |

行内元素字段：

| 字段 | 所属 | 含义 | DITA 对应 |
|---|---|---|---|
| `text` | `b`/`i` | 强调的文本 | 元素内容 |
| `href` | `xref` | 引用目标：Topic URN，可带 `#元素id` 片段（指向 `fig` 等带 id 的元素） | `@href`/`@keyref` |
| `text` | `xref` | 链接显示文本 | 元素内容 |

**元素准入三条**（进封闭集必须同时满足）：① 真实文档证据（扫描或审核清单出现）；② 车机有明确渲染方案；③ 有确定性抽取规则或人工流程。不满足 → 挂"已知未支持"清单，遇到时进审核。

**已知未支持**（等 B/C 手册扫描证据，按准入三条扩张）：`dl`（定义列表）、`glossentry`（术语条目 topic 类型——B/C 若有术语表则进封闭集）、`pre`/`screen`/`lines`（固定格式文本）、`uicontrol`/`menucascade`（UI 菜单路径）、`term`（术语）、hazard 结构化（`typeofhazard/consequences/howtoavoid`）、`choicetable`（步骤选择表）。`shortdesc` 不进封闭集（从首段派生，属派生物）。

### 2.3 标识体系（照行业标准的共同实践）

| 对象 | 格式 | 示例 |
|---|---|---|
| Manual | `urn:xcmg:manual:{model}-{doc}` | `urn:xcmg:manual:xc975-opm` |
| Edition | `urn:xcmg:edition:{manual}:{version}` | `urn:xcmg:edition:xc975-opm:202608` |
| Topic | `urn:xcmg:topic:{manual}:t{4位序号}` | `urn:xcmg:topic:xc975-opm:t0057` |
| Asset | 包内相对路径 | `img/A_2_5_1_01.png` |
| FaultCode | 厂商故障码 + J1939 映射 | `WL-027` / `j1939.spn` |
| MaintenanceRule | `M-{hours}-{2位序号}`，首保 `M-{hours}-FIRST-{n}` | `M-250-03` |
| DiagnosticRule | `DR-{3位序号}`，原因 `DR-xxx-C{2位}` | `DR-015` / `DR-015-C01` |

稳定性规则：Topic ID 在 Manual 范围内分配、**跨 Edition 不变**（改版重跑按标题+内容匹配复用旧 ID，废弃 ID 永不复用）；章节号降为 `props.chapterNo` 显示锚；一切跨引用（`source`）用 Topic ID。

## 3. 打包与存储：Readium RWPM 的实施剖面

### 3.1 RWPM 标准结构

`metadata`（DCMI：identifier/title/language/modified + 命名空间扩展）+ `readingOrder`（阅读顺序）+ `resources`（资源清单，任意 media type）。

### 3.2 本规范的 manifest（参照实现）

```json
{
  "metadata": {
    "identifier": "urn:xcmg:edition:xc975-opm:202608",
    "title": "XC975-EV 操作与保养手册",
    "language": "zh-CN",
    "modified": "2026-11-07T11:00:00Z",
    "author": "刘浩",
    "xcmg": { "docCode": "A", "product": "XC975-EV/dry-bridge",
              "schemaVersion": "2", "counts": { "topics": 161, "faultCodes": 205 } }
  },
  "readingOrder": [
    { "href": "topics/t0001.json", "type": "application/json", "title": "1 总则" },
    { "href": "topics/t0057.json", "type": "application/json", "title": "2.5.1 日常检查" }
  ],
  "resources": [
    { "href": "index.json", "type": "application/json" },
    { "href": "fault_codes.json", "type": "application/json" },
    { "href": "img/A_2_5_1_01.png", "type": "image/png", "xcmg:sha256": "…" }
  ]
}
```

**字段说明**：

| 字段 | 含义 | RWPM 对应 |
|---|---|---|
| `metadata.identifier` | Edition URN——数据包唯一标识 | DCMI `identifier` |
| `metadata.title` / `language` / `modified` / `author` | 标题 / 语言（`zh-CN`）/ 最后修改时间（ISO 8601）/ 作者 | DCMI 标准字段 |
| `metadata.xcmg.docCode` / `product` / `schemaVersion` / `counts` | 手册代号 / 适用变体 / 格式版本 / 规模计数（黄金断言基数） | 命名空间扩展 |
| `readingOrder` | 阅读顺序资源列表（`topics/tXXXX.json`，按 `seq` 排序） | RWPM 必填集合 |
| `resources` | 全部资源清单：`href` + `type`（media type）+ `xcmg:sha256`（逐文件校验和） | RWPM + 扩展 |

- 完整性：逐文件 `xcmg:sha256`（严于 EPUB——EPUB 无逐文件校验和）；平台期升级 TUF/Uptane 签名；
- 车机落地：数据包放文件系统数据目录（不进 qrc），启动验校验和，失败不启用、回退上一可用包；
- **内容包是数据，不含可执行代码**（QML/脚本一律不进包）——包不是绕过 App 审核的代码更新通道；这是行业受控离线产品的共同安全边界（Accuris/Cat 模式，调研文档 §8.2）。

### 3.3 包内布局与粒度

**包内布局**（物理粒度——**不是一整个巨大 JSON**）：

```text
package/
├── manifest.json            # RWPM 清单
├── index.json               # 目录索引（id/title/parent/seq/chapterNo——TreeView 数据源，启动只读它）
├── topics/
│   ├── t0057.json           # 一个 Topic 一个文件
│   └── …（每手册 77~261 个）
├── fault_codes.json         # 实体表（查表数据整体载入，保持单文件）
├── maintenance_rules.json
├── audit.json
└── img/
```

**粒度规则**：

- **Topic = 一文件**：车机打开一节只读一个文件（按需加载）；深链直接定位文件；OTA 可只更新变化的 topic。这**正是 RWPM/EPUB 的标准粒度**——readingOrder 本来就是资源列表，EPUB 每章一个 XHTML 文件；
- **实体/规则表 = 单文件**：查表数据本就整体载入内存/SQLite，拆分无意义；
- **index.json**：目录树最小索引（不含正文块），启动只读它画目录，点开章节再读对应 topic 文件——启动解析量从整本 5~15MB 降到几十 KB；
- 当前管线产出单个 `tree_A.json` 是第一批实现便捷，迁移时按此布局拆分（抽取逻辑不变）。

### 3.4 数据划分与存储映射

逻辑划分见 §7（内容单元 / 实体 / 规则三子模型）；本表回答"**每份数据落到哪个文件、哪个存储、谁是权威**"——一个 Edition 的全部数据去向一览：

| 逻辑数据 | 车机包内文件 | 车机消费方式 | 后端存储 | 权威性 |
|---|---|---|---|---|
| Topic[] | `topics/tXXXX.json`（一文件一 Topic） | 手册 Tab 按需加载 | MySQL `topics` 表 | 权威 |
| 目录索引 | `index.json` | 启动画 TreeView | —（可由 Topic 集重建） | **派生** |
| FaultCode[] | `fault_codes.json` | 故障 Tab 整体载入查表 | MySQL `fault_codes` 表 | 权威 |
| MaintenanceRule[] | `maintenance_rules.json` | 保养 Tab 规则引擎 | MySQL 表 | 权威 |
| Baseline[] | `baselines.json` | `auto_compare` 判卷 | MySQL 表 | 权威 |
| Checklist[] | `checklists.json` | 电子点检表 | MySQL 表 | 权威 |
| DiagnosticRule[] | `diagnostic_rules.json` | 诊断画布（在线执行，后端为主） | MySQL 表 | 权威 |
| Asset[]（图片） | `img/`（一图一文件） | Image delegate | MinIO / 对象存储 | 权威（转码产物） |
| manifest | `manifest.json` | 启动验完整性 | MySQL 版本记录 | 权威 |
| 审核清单 | `audit.json` | **车机不消费**（人工质量门用） | 审核 workflow | 权威（过程数据） |
| RAGChunk[] | **不在车机包** | — | RAGFlow 知识库 | **派生**（从 Topic 生成，§7） |
| SearchRecord[] | **不在车机包** | — | Elasticsearch 索引 | **派生** |

**权威性两阶段**（诚实声明）：

- **第一批（现在）**：管线产物即权威——包文件与 MySQL 副本由**同一次抽取同源生成**；车机只认包文件，MySQL 是管理/服务化副本；
- **平台期**：MySQL 规范内容库升为**服务权威**，包文件、RAGChunk、检索索引全部由它派生重建（§7 派生物铁律）。

### 3.5 存储格式细则

| 项 | 规则 |
|---|---|
| 文本编码 | 一切 JSON/文本文件 **UTF-8（无 BOM）**，换行 LF |
| JSON 书写 | 中文直接存中文（不转 `\u` 转义）；缩进 2 空格；一个文件一个 JSON 文档（topic 文件 = 单个对象，实体/规则表 = 数组） |
| topic 文件命名 | `topics/tXXXX.json`，XXXX = Topic URN 的 4 位序号（§2.3），零填充 |
| 图片命名 | `img/` 下包内唯一即可（管线现用 `{docCode}_{chapterNo}_{seq}.{ext}`）；manifest `resources` 逐文件收录 + sha256 |
| 图片格式 | 线稿 PNG、实拍 JPEG（q≈85）；目标宽 800px（车机屏宽）；EMF/WMF 抽取时转 PNG |
| MySQL 副本 | 表结构随迁移定；原则：与包文件同源生成、字段名与本规范一致 |

### 3.6 每个文件的生产方式（数据契约级规则）

生产链（应用层实现，详见随车助手应用文档 §6.2）：`校验 → 解析 → 编号 → 表格分类 → 图片提取 → 产品切分 → 打包 → 审核`。本节回答：**包内每个文件，从源文档的什么内容、按什么规则解析出来**——这是数据契约的一部分；启发式校准、DRM 校验、LibreOffice 转换等实现细节属应用层。

| 包内文件 | 从源文档的什么内容生产 | 生产规则（怎么解析） | 权威/派生 | 状态 |
|---|---|---|---|---|
| `topics/tXXXX.json` | 手册正文的每个章节（标题 + 段落/表格/图片/警告框） | ① 标题识别（样式名大小写不敏感）→ 位置推导编号 → 分配稳定 ID；② 章节内容按文档流顺序规整为块：段落→`p`、警告框→`note`、●清单→`ul`、操作步骤→`steps`、插图→`fig`、数据表→`simpletable`/`table`、超链接→`xref`、加粗→`b`；③ 归不进封闭集的内容进审核清单，绝不透传 | 权威 | ✅ 第一批（xref/b/table span 为升级项） |
| `index.json` | 从 Topic 集派生 | 取每个 Topic 的 `id/title/parent/seq/chapterNo` 组成目录树索引，**不含正文块** | **派生** | 🔧 打包期生成（迁移项） |
| `fault_codes.json` | A 3.10 / B 1.8.2 的故障码表 | ① 表格分类为 `fault_code`；② 表头映射（精确+子串：`序号`/`故障代码`→`code`、`故障触发条件`→`triggerCondition`…）；③ 合并单元格续行**前向填充**；④ 同码多等级行**折叠取最高**（进审核）；⑤ 空措施打 `auditFlag` | 权威 | ✅ 第一批（205 条实测验证） |
| `maintenance_rules.json` | A 3.3.2~3.3.8 周期小节的 ● 清单 + 累积/首保短语；C 6.x EU 变体 | ① 小节标题携周期（"每250小时/每月"→ `interval` + `calendar`）；② ● 段落逐条成规则；③ "同时进行每10、50、100小时"→ `accumulates`；④ "对于第一个250小时，还需进行："→ `one_time_first_cycle`；⑤ 匹配不上进审核，不猜 | 权威 | ✅ 第一批（60 条实测验证） |
| `baselines.json` | B 手册的测压点/传感器标定/温度限值表 | 表格分类 + 表头映射（对象/测点/正常值） | 权威 | ⏳ 第二批 |
| `checklists.json` | A 2.5.1 日常检查 + C 4.8.4 高压启动检查表 | ● 清单/表格行 → 检查项 | 权威 | ⏳ 顺手做（赠品） |
| `diagnostic_rules.json` | A 3.9 现象表 + B 液压/制动故障表 + B 诊断方法论 | ① 现象/原因/措施确定性解析；② 步骤分解 + 四分类打标：LLM 辅助 + **人工审**；③ `verification` 段按行业模式模板注入（`origin: "industry-pattern"` 标注，过审） | 权威 | ⏳ 第二批 |
| `img/` | docx 媒体部件（段落锚点 + **表格内嵌图**） | ① 按锚点所属章节命名落盘；② EMF/WMF→PNG（LibreOffice）；③ 宽 >800px 缩放；④ 同一部件多处引用只落盘一次 | 权威（转码产物） | ✅ 第一批（268 张全覆盖实测） |
| `manifest.json` | 打包时计算 | RWPM 结构：`readingOrder` 按 `seq` 列 topic 文件；`resources` 逐文件 + sha256；`counts` 规模计数（黄金断言基数） | 权威 | ✅ 第一批（拆分布局为迁移项） |
| `audit.json` | 全流程副产物 | 各阶段审核项汇总（陈旧目录 / 空措施 / 矢量图待转 / 前缀未定 / 行内拍平…） | 过程数据 | ✅ 第一批 |
| RAGChunk（**不入包**） | Topic 正文 | 编号注入后的章节文本化 + `product`/`audience` 元数据 → RAGFlow 知识库 API | **派生** | ⏳ 第二批 |

**两条生产原则**：

- **同源生成**：Topic（给人读）与实体/规则（给程序查/执行）从**同一处源内容一次抽取**产出，经 `source` 互链——不是两套流程各抽一遍；
- **派生物在打包期/入库期生成**：`index.json` 打包时从 Topic 集派生，RAGChunk 入库时从 Topic 派生——权威数据变了重跑即得，永不手工维护。

## 4. 故障域：J1939 + OTX + DITA troubleshooting 的实施剖面

### 4.1 行业实现模式（四大诊断工具的共同架构）

BMW ISTA、VW ODIS、Mercedes XENTRY、Toyota Techstream 是同一个模式，每步都有标准归属：

```text
① 整车识别：VIN/SN → as-shipped 配置（决定哪些 ECU、哪些测试计划适用）
② 整车问询：读全车 ECU 故障存储 + 实时数据 + freeze frame（故障瞬间工况快照）
   ← SAE J1939-73 诊断消息族（活动码 DM1 / 历史码 DM2 / 清码 DM3）；通信细节 ASAM ODX（车控域）
③ 测试计划生成：故障码 + 客户陈述（现象）→ 组装有序测试计划
   —— 测试计划 = 数据库中的结构化可执行过程（BMW 称 ABL"可执行模块"），不是文档
   ← ISO 13209 OTX（可执行测试序列交换格式）
④ 引导执行：自动问询 / 带期望值与判据的引导测量 / 文档引用（维修指导）/ 用户交互
⑤ 验证闭环：修复后清码 + 复测，以复测通过作为修复证明（ISTA"清故障存储 + 快速测试"）
```

**值得采用的两个行业细节**：

- **freeze frame**（源于 OBD 实践）：故障发生瞬间的工况快照，对付间歇性故障——问询阶段读取，诊断步骤可引用（§4.5 落为 B4 信号需求）；
- **远程录制**（John Deere Service Advisor Remote 模式）：专家远程查看/录制机器数据——平台期能力，本规范仅预留会话数据，不定义格式。

**知识形态的行业答案**：测试计划 = 数据库结构化可执行过程；维修手册/TSB（技术服务公告）= 文档；FTA/FMEA 工作表 = 上游。混合形态各归其位——这正是本规范"实体/规则 vs Topic"分层的行业依据。TSB 将来作为 Topic 的一类来源接入。

### 4.2 故障码注册表（对齐 J1939/J2012 + 行业注册表模式）

行业注册表模式（码→定义→触发条件→严重度→措施）无官方 schema，各 OEM 均为此形状；**身份字段**对齐 J1939（`spn`/`fmi`——与诊断仪/上位机互通的钥匙）。

```json
{
  "id": "WL-027",
  "controller": "行走电控",
  "code": 27,
  "j1939": { "spn": null, "fmi": null },
  "name": "堵转保护",
  "triggerCondition": "转速小于20，力矩大于2800，持续30秒",
  "severity": 3,
  "remedy": "停车，不可长时间低速大扭矩使用电机。",
  "product": "XC975-EV/dry-bridge",
  "audience": "operator",
  "source": ["urn:xcmg:topic:xc975-opm:t0142"],
  "src": [1116],
  "diagnostic": null,
  "auditFlag": null
}
```

- `j1939.spn/fmi`：待车控团队确认 ECU 故障协议后填充；
- `diagnostic`：指向 DiagnosticRule 入口（§4.4）——**有诊断流的码才非空，查码即进树**；无诊断流的码（手册现实：205 条码是平表、现象表仅 30 现象）诚实保持 null，退化为"记录 + 措施"，不凭空造树节点；
- 同一条码在 Edition 内两个同源形态：Topic 内 `simpletable`（给人读）与本实体（给程序查），经 `source` 互链；**查询场景的权威永远是实体表**。

**字段说明**：

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `id` | string | ✓ | 厂商故障码（`前缀-码`，如 WL-027；前缀除行走电控=WL 外待确认） |
| `controller` | string | ✓ | 控制器：行走电控/液压电控/水冷机组/动力电池/多合一 |
| `code` | int | ✓ | 数字码 |
| `j1939.spn` / `j1939.fmi` | int? | ○ | J1939 身份映射（待车控团队确认 ECU 协议后填充） |
| `name` | string | ✓ | 故障名称 |
| `triggerCondition` | string? | ○ | 触发条件 |
| `severity` | int? | ○ | 故障等级 1/2/3；3 = 停机/联系厂家，驱动界面紧急度 |
| `remedy` | string? | ○ | 解决措施；为空 → `auditFlag = "待审-空措施"` |
| `product` / `audience` | string | ✓ | 适用性（§6） |
| `source` | URN[] | ✓ | 来源 Topic 列表（锚体系） |
| `src` | int[] | ○ | 版面流元素序号（工作台溯源） |
| `diagnostic` | ref? | ○ | 指向 DiagnosticRule 入口（§4.4，查码即进树；无诊断流保持 null） |
| `auditFlag` | string? | ○ | 质量标记（null = 无待审项） |

### 4.3 诊断树格式（对齐 ISO 13209 OTX 语义子集 + DITA troubleshooting）

**标准如何做**：OTX 定义可执行测试序列的完整控制流——核心数据模型是过程式的（参数化过程、变量与数据类型、循环/分支/返回、过程调用、异常处理；语法 UML 类图 + XML Schema，出处：ISO 13209-2:2022）；DITA troubleshooting topic 定义排障内容形态——标准结构为 `troubleshooting > troublebody > condition + troubleSolution*`，每个 `troubleSolution` 配对一组 `cause` 与 `remedy`（出处：DITA 1.3 Part 2 §3.10.4）。本规范的 `causes[]` 条目即 `troubleSolution` 的 JSON 绑定。

**本规范的采用**：手册派生的诊断树用不到 OTX 全集，采用其**语义子集**——原因级分支 + 原因内顺序步骤 + 通过判据 + 验证闭环；内容形态对齐 DITA troubleshooting。需要更复杂控制流时按 OTX 扩展，格式不推倒。

```json
{
  "el": "troubleshooting",
  "id": "DR-015",
  "title": "整车无法上高压",
  "system": "电气系统",
  "synonyms": ["上不了高压", "无法上电"],
  "entryCodes": [],
  "product": "XC975-EV/dry-bridge",
  "audience": "technician",
  "props": { "docCode": "A", "chapterNo": "3.9.1" },
  "causes": [
    {
      "id": "DR-015-C01",
      "condition": "蓄电池箱损坏或电力不足",
      "steps": [
        { "el": "step", "type": "auto_query", "cmd": "读取动力电池SOC",
          "signal": "SOC", "passCriteria": "SOC>=20%" },
        { "el": "step", "type": "ask_user", "cmd": "检查蓄电池箱外观及接线有无破损、松动",
          "passCriteria": "无破损且接线牢固" },
        { "el": "step", "type": "physical", "cmd": "更换蓄电池箱或充电",
          "refTopic": "urn:xcmg:topic:xc975-smm:t0066" }
      ]
    }
  ],
  "verification": {
    "props": { "origin": "industry-pattern" },
    "steps": [
      { "el": "step", "type": "auto_query", "cmd": "清除故障存储", "signal": "clearDTC" },
      { "el": "step", "type": "auto_query", "cmd": "重读故障存储", "signal": "activeDTC",
        "passCriteria": "无活动码" }
    ]
  },
  "source": ["urn:xcmg:topic:xc975-opm:t0155"],
  "src": [1201],
  "auditFlag": null
}
```

**步骤类型**（对齐 ISTA 步骤分类 / OTX action）：

| `type` | 行业对应 | 专用字段 | 执行方 |
|---|---|---|---|
| `auto_query` | 自动问询（OTX 服务调用） | `signal`、`passCriteria?` | 系统读车端数据（经 B4 映射） |
| `auto_compare` | 引导测量（期望值 + 判据） | `signal`、`baselineRef`、`passCriteria?` | 系统读数对照 Baseline（§5） |
| `ask_user` | 用户交互（OTX-HMI） | `passCriteria`、`options?` | 界面问用户观察结果 |
| `physical` | 文档引用（维修指导） | `refTopic` | 动手作业，链到拆装 Topic |

**验证闭环**（`verification`，规则级收尾段）：

- 即 ISTA"清码 + 复测"模式，以复测通过作为**修复证明**；
- 手册通常无此文字——默认由管线按行业模式模板注入，`props.origin = "industry-pattern"` 标注非手册来源，**人工审核确认**（不猜原则同样适用于"行业注入"）；
- 执行语义：任一原因的修复动作完成后进入 verification，全部通过才关闭本次诊断。

**执行语义**：原因按序尝试，步骤 `passCriteria` 不通过 = 该原因未确认 → 下一原因；确认后执行修复步骤 → 进 verification。

**字段说明**：

| 字段 | 含义 |
|---|---|
| `id` | 规则 ID `DR-xxx`；原因 `DR-xxx-Cxx` |
| `title` / `system` | 现象名 / 所属系统 |
| `synonyms` | 口语同义词（入口 2 的 LLM 匹配用） |
| `entryCodes` | 码入口：哪些故障码直接进这棵树（与 `FaultCode.diagnostic` 双向焊接） |
| `causes[].condition` | 原因描述（DITA `cause`） |
| `causes[].steps[]` | 确认与修复步骤序列 |
| `step.type` | `auto_query` / `auto_compare` / `ask_user` / `physical`（四分类表见上） |
| `step.cmd` | 步骤指令 |
| `step.signal` | 读取的信号键（B4 映射；`auto_query`/`auto_compare`/verification 用） |
| `step.baselineRef` | `auto_compare` 引用的 Baseline ID（判卷标准） |
| `step.passCriteria` | 通过判据（缺省：`auto_compare` 用 `normalValue`，`ask_user` 由用户确认） |
| `step.refTopic` | `physical` 链到的拆装 Topic URN |
| `verification` | 验证闭环段（清码 + 复测判空 = 修复证明）；`props.origin = "industry-pattern"` 标注非手册来源，人工审核 |
| `source` / `src` / `auditFlag` | 脊柱字段（同实体） |

### 4.4 统一诊断流：两个入口，一棵树

```text
入口1 输码（精确 · 离线）→ FaultCode 记录 ──┬─ 无诊断流 → 显示记录 + 措施（第一批的离线终点）
                                           └─ 有诊断流 → diagnostic 引用 → 进树
入口2 描述现象（口语 · 在线）→ LLM 匹配现象（含 synonyms）→ 进树
                                                        ▼
                                    DiagnosticRule（原因 → 步骤 → verification）
                                    ├─ auto_query 读码 → entryCodes/codeRef 命中 → 跳对应分支
                                    ├─ auto_compare → Baseline 判卷
                                    ├─ ask_user → 界面问答
                                    └─ physical → refTopic → 拆装 Topic
```

`FaultCode.diagnostic` 与 `DiagnosticRule.entryCodes` **双向焊接**；数据上引用连接而非物理嵌套——保住离线查码（第一批交付）、J1939 互通面与"不猜"原则。

### 4.5 信号依赖（B4 对接需求清单）

`auto_query` / `auto_compare` / `verification` 的执行依赖 B4 信号映射表（车控团队提供）。按 §4.1 行业模式，问询类信号至少覆盖：

| 信号类别 | 行业对应 | 用途 |
|---|---|---|
| 实时数据（SOC/油温/压力…） | J1939 PGN 实时参数 | auto_query / auto_compare |
| 活动故障码 / 历史故障码 | J1939-73 DM1 / DM2 | 问询、verification 复测 |
| 清除故障存储 | J1939-73 DM3 | verification 清码 |
| **freeze frame 快照** | OBD freeze frame 实践 | 间歇性故障诊断 |

此清单随 B4 对接一并交车控团队确认。

## 5. 保养与基准：无标准层的最小自造

诚实声明：保养规则与基准值无行业标准格式（SAP PM / Maximo 均为私有 schema），本层最小自造、英文字段名。

**MaintenanceRule**：

```json
{
  "id": "M-250-03",
  "product": "XC975-EV/dry-bridge",
  "trigger": { "type": "interval", "hours": 250, "calendar": "monthly", "duePolicy": "whichever-first" },
  "content": "检查电池组电压状态",
  "accumulates": ["M-10-*", "M-50-*", "M-100-*"],
  "source": ["urn:xcmg:topic:xc975-opm:t0131"],
  "src": [834],
  "auditFlag": null
}
```

`trigger.type` 封闭集：`interval` / `one_time_first_cycle` / `condition`（条件规则，LLM 抽取 + 人工审）。

**Baseline**（auto_compare 的判卷依据，维修类手册独有）：

```json
{ "id": "BL-01", "type": "pressure", "object": "工作压力", "measurePoint": "多路阀测压口",
  "normalValue": "20.5±0.5MPa", "product": "XC975-EV/dry-bridge",
  "source": ["urn:xcmg:topic:xc975-smm:t0088"], "src": [912], "auditFlag": null }
```

**Checklist**（检查单）：

```json
{ "id": "CL-A-01", "title": "日常检查", "items": ["检查冷却液液位", "…"],
  "product": "XC975-EV/dry-bridge", "audience": "operator",
  "source": ["urn:xcmg:topic:xc975-opm:t0057"], "src": [801], "auditFlag": null }
```

**字段说明**：

- **MaintenanceRule**：`trigger.type`（封闭集 `interval`/`one_time_first_cycle`/`condition`）；`trigger.hours`（周期小时数）；`trigger.calendar`（日历周期 `daily`/`weekly`/`monthly`/`yearly`，可空）；`trigger.duePolicy`（`whichever-first`：小时与日历先到为准）；`content`（保养内容）；`accumulates`（低周期规则引用，如 `["M-10-*","M-50-*"]`——高周期提醒包含低周期全部项目）。
- **Baseline**：`type`（基准类型：`pressure`/`temperature`/`resistance`/`voltage`…）；`object`（对象，如"工作压力"）；`measurePoint`（测点，如"多路阀测压口"）；`normalValue`（正常值含公差，如 `20.5±0.5MPa`——`auto_compare` 的判卷标准）。
- **Checklist**：`title`（清单名）；`items`（检查项列表——车载屏电子点检表的数据源）。

照 DITA profiling 实践 + 行业交付模式（Cat SIS 2.0 的 SN 驱动）：

| 字段 | 值域 | 示例 |
|---|---|---|
| `product` | `{机型}/{配置}` | `XC975-EV/dry-bridge`、`XC975-EV/wet-bridge+eh-proportional` |
| `audience` | `operator / technician` | |
| `props.market` | `CN / EU` | |

**SN 硬约束流程**（交付期执行；检索、渲染、规则求值、离线包签发全部遵守）：

```
输入 SN → 查 SN 注册表 → 得 VariantProfile(product, audience, market) → 过滤一切数据
```

适用性是权限之外的**硬约束**，不允许靠搜索排序"尽量把正确版本排在前面"。

## 7. 领域模型总图

```text
SourceDocument（不可变原件：docx/doc 及其哈希）
        │ 抽取（确定性管线，应用层实现）
        ▼
Manual（手册：机型 + 文档类型的逻辑概念）
  └─ Edition（不可变版本：某手册某版次的全部权威数据）
       ├─ Topic[]（内容单元，DITA topic 剖面）
       ├─ FaultCode[]（实体，J1939 身份 + 注册表模式）
       ├─ Baseline[] / Checklist[]（实体）
       ├─ MaintenanceRule[]（规则，最小自造）
       ├─ DiagnosticRule[]（规则，OTX 语义子集 + DITA troubleshooting）
       └─ CrossRef[]（显式跨引用，后续）
        │ 派生（可随时重建）
        ├── RAGChunk[]（Topic 的第二序列化，带 product/audience 供检索过滤）
        ├── SearchRecord[]（检索索引）
        └── OfflinePackage（RWPM 打包 + 逐文件 sha256）
```

**派生物铁律**：RAGChunk 永不作为事实权威——问答按意图路由，查码/查值走工具调用查实体表，理解类走检索。

## 8. 质量与版本

- **封闭类型断言**：未知 `el` / 未知 `type` / 未知 `trigger.type` 计数 = 0；
- **黄金断言**（每手册一组，改版重跑即验）：规模计数 + 跨引用完整（一切 `source`/`refTopic`/`baselineRef`/`diagnostic` 可解析到存在的对象）；
- **审核工作流**：`auditFlag` 非空进人工质量门；`origin: "industry-pattern"` 的注入内容同样过审；未过审的 Edition 不得发布；
- **版本演进**：`schemaVersion` 递增，不兼容变更附迁移规则与旧版读取期限。

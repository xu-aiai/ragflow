## 1. 背景

### 1.1 产品定义

**随车助手**：车载显示屏上的一个 App，四个入口——📖 手册、💬 问答、⚠️ 故障、🔧 保养。

一句话：**把三本手册变成机器自带的一个助手——能翻、能问、能查故障、能提醒保养。**

设计原则（对标工业界成熟模式，但只取其数据模型、不取其产品规模）：

- **厚数据、薄运行时**：一次性抽取管线产出结构化数据，四个功能的运行时都做薄；
- **结构化数据与语料分离**："给程序算的数据"（树/码表/规则）进 MySQL 和屏幕本地包，"给 LLM 查的语料"进 RAGFlow 知识库；
- **规范先行、产品为视图**：先定义通用数据规范（脊柱 + 内容单元/实体/规则三子模型，§3），四个 Tab 等产品功能都是规范之上的视图——新产品加视图，新机型重跑管线，规范与管线不动；
- **确定性优先**：能确定性抽取的全部确定性抽取，LLM 只用于两小块（步骤分解、条件规则），且必须人工审核（安全相关内容）。

```

   │
   ▼
抽取管线（一次性建设，手册改版后重跑）
   │
   ├─→ A 文档树 ─────────→ 📖 手册 Tab（本地渲染，离线可用）
   ├─→ B1 故障码注册表 ──┐
   ├─→ B2 现象-原因-措施树 ├→ ⚠️ 故障 Tab（查码本地离线；现象诊断走 LLM）
   ├─→ B3 基准值表 ───────┘
   ├─→ C 保养规则库 ─────→ 🔧 保养 Tab（本地规则引擎，离线可用）
   ├─→ D RAG 语料块 ─────→ RAGFlow 知识库 → 💬 问答 Tab（云端 LLM）
   └─→ E 审核清单 ───────→ 人工过审（质量门）

B4 信号映射表：由车控团队提供（唯一不来自手册的数据）
```

**存储与运行位置**：

| 数据 | 位置 | 理由 |
|---|---|---|
| A / B1 / B3 / C | 屏幕端本地数据包（JSON，QML 直读）+ 后端 MySQL | 手册浏览、查码、保养提醒必须离线可用 |
| B2 | 后端 MySQL | 现象诊断依赖 LLM，天然在线 |
| D | RAGFlow 知识库 ×1~2（国内版 / EU 版分库） | 检索问答；按机型变体选库 |
| B4 | 后端配置 | 车端信号对接 |

**RAGFlow 的角色**：一个知识库（语料检索）+ Agent 画布编排（问答画布、故障诊断画布：Categorize / Retrieval / Invoke / ExeSQL / UserFillUp / Message 组件）。RAGFlow 不是结构化数据的存储底座。

## 3. 通用数据规范与产品视图

### 3.0 总纲：规范先行，产品为视图

所有文档拆成两条轨道——"给程序算的"结构化数据、"给 LLM 查的"语料——两者共享同一套**通用数据规范**：一个脊柱 + 三个子模型。产品功能不定义数据格式，它们是规范之上的视图：

| 产品功能 | 用规范的哪部分 | 视图方式 |
|---|---|---|
| 手册 Tab | 内容单元 | 渲染（QML delegate） |
| 问答 Tab | 内容单元 + 实体 | 检索 + ExeSQL 工具查询 |
| 故障 Tab·输码查询 | 实体（B1） | 本地查表 |
| 故障 Tab·描述现象 | 规则（B2）+ 实体（B3）+ 信号（B4） | 执行 |
| 保养 Tab | 规则（C） | 执行 |
| 全部功能的深链 | 锚体系 | 引用 |
| 电子点检表（赠品） | 实体（检查单） | 渲染 |

新产品 = 加一种视图（或实体模型加一种 record）；新机型 = 重跑管线。规范与管线不动。

### 3.1 脊柱（一切数据单元共享的四个共性）

| 共性 | 机制 | 作用 |
|---|---|---|
| 锚体系 | 内容单元自带 `section_id`；实体/规则经 `来源`（section_id 列表）回指；`src`（版面流元素 ID）供工作台点击溯源 | 深链、溯源、跨引用完整性断言 |
| 变体元数据 | 单元级 `适用变体`（缺省继承数据包 manifest 的市场/配置/受众/SN/版本，附录 B.3） | 按机器过滤，防配置串线 |
| 质量标记 | 单元级 `审核标记` + 包级 audit.json + 黄金断言 | 人工质量门（§3.E） |
| 封闭类型 | 块集 / 实体 schema / 触发语义封闭，未知类型进审核清单绝不透传 | 可校验、可渲染 |

### 3.2 内容单元模型（给人读的）

章节（Section）= 锚（section_id / seq / 面包屑）+ 有序内容块序列。块类型封闭集六种（见 §3.A 表）。**D 语料块是内容单元的第二种序列化**——同 section_id、同变体元数据，一个给渲染、一个给检索；不是另一份数据。

### 3.3 实体模型（给程序查的记录）

注册表类数据统一为 typed record：唯一 ID + 业务字段 + 脊柱字段（来源 / 适用变体 / 审核标记）。已定义：故障码（B1）、基准值（B3）、检查单；新增实体 = 加一种 record schema + 一个视图。

### 3.4 规则模型（给程序执行的）

统一为：触发语义（`interval` / `one_time_first_cycle` / `condition`）+ 内容/动作 + 累积引用 + 脊柱字段。诊断步骤四分类（auto_query / auto_compare / ask_user / physical）见 §3.B2。

### 3.5 规范 ↔ DITA 映射（逃生门）

| 规范概念 | DITA 对应物 |
|---|---|
| 内容单元（章节） | topic（concept / task / reference / troubleshooting） |
| `para` / `list` / `steps` | `<p>` / `<ul>` / `<task><steps><step><cmd>` |
| `warning`（注意/警告/危险） | `<note type="caution/warning/danger">` |
| `table` / `image` | `<simpletable>` / `<fig><image>` |
| `section_id` | topic `@id` |
| 变体元数据 | profiling 属性（`@product`/`@audience`）+ DITAVAL |
| 文档树 / 面包屑 | `<map><topicref>` |
| 实体 / 规则 | DITA 之外（行业对应 SAE J2012 / SAP PM） |

JSON 是语法，规范才是资产：上 DITA 创作或对接外部系统时按表机械转译；`schema_version` 保障升级有据。

### 3.6 产品视图定义（原"七样数据产品"）

以下各视图是 §3.0~3.5 规范的实例化 schema，兼作规范的验收用例——规范改动后逐条检验"各视图仍可推导"。

### A. 文档树 → 手册 Tab + 全部功能的深链底座

- **来源**：三份手册全部正文（A 159 节点 / B 77 / C 261）
- **抽取方式**：确定性。编号注入（目录映射 + 位置推导 + 冲突报告）→ 按标题层级切树 → 内容规整为类型化块（图片即块）
- **数量**：约 500 个章节节点
- **渲染目标**：QML（Qt 6），1280×800 竖屏（宽 800）

```json
{
  "section_id": "A-2.5.1",
  "seq": 57,
  "章节号": "2.5.1",
  "标题": "日常检查",
  "层级": 3,
  "parent": "A-2.5",
  "面包屑": "2 操作 > 2.5 起动之前 > 2.5.1 日常检查",
  "blocks": [
    {"type": "warning", "level": "警告", "text": "机器在5s～10s内起动不了，应等1min后再重复起动。"},
    {"type": "para", "text": "为了最大限度地延长机器的使用寿命，先进行全面的日常检查后再上机起动机器。"},
    {"type": "list", "style": "check", "items": ["检查冷却液液位", "检查液压油油位"]},
    {"type": "image", "file": "img/A_2_5_1_01.png", "图号": "图2-38", "题注": "图2-38 日常检查位置"}
  ]
}
```

**块类型封闭集**（渲染字母表，QML 每种块一个 delegate）：

| 块类型 | 对应手册内容 | QML 渲染 |
|---|---|---|
| `para` | 普通段落 | `Text`，App 统一字体字号 |
| `image` | 插图 + 图号 + 题注 | `Image`（PreserveAspectFit，宽 800），点击全屏 `PinchArea` 捏合缩放 |
| `table` | 真数据表（扭矩/针脚/测压值） | `TableView`，可横向滑动 |
| `warning` | 注意/警告/危险框（原文为表格形态） | 全宽色块 + 图标，最醒目样式 |
| `steps` | 操作程序（先……再……） | 编号步骤列表 |
| `list` | ● 检查清单 | 清单样式 |

**要点**：

- `section_id` 是全系统深链的锚点（问答/故障/保养跳转手册都用它）；`seq` 是文档流顺序，排序/导航一律用它，章节号只做展示与锚点；
- **丢掉 Word 的皮，只留结构**：字体/字号/颜色/对齐在抽取时全部丢弃，由车机设计系统接管（车机自带中文字体，宋体/黑体在目标机不存在）。"格式不乱"由封闭块集保证——App 只渲染它认识的六种块；
- **分类不了的进审核清单，绝不透传**：黄金测试断言包内未知类型块数 = 0；
- 图片即块：文中位置 = 块顺序；EMF/WMF 在抽取时转 PNG，按 800px 宽转码；题注（"图N-N"段落）就近并入图片块；
- A/C 的警告框是表格框形态（"注意/警告"行），C 有语义样式（Achtung! 等），统一归一为 `warning` 块的 level 枚举（注意/警告/危险）；
- `源页码` 字段取消：docx 无固有页码，车机 UI 亦无用途。

**步骤执行类型四分类**（简版 ISTA 模式）：

| 类型 | 含义 | 手册中的真实例子 |
|---|---|---|
| `auto_query` | 自动读车端数据 | "根据仪表显示屏上的代码来判断故障"（B 电气表）；"检查动力电池电量，不低于20%"（A 2.5.1） |

**要点**：块必须带 `section_id` 和面包屑——这是"回答完一键跳到手册 2.5.1"的前提；变体元数据用于按机型选库检索，防止干桥用户召回湿桥内容。

## 6. 第一批实现方案（2026-11-02 评审定稿）

第一批范围：**A 文档树 + B1 故障码 + C 周期规则**，全部确定性抽取，共用一条管线。C 的散文条件规则（LLM+人工审）推迟到第二批与问答一起做。

### 6.1 数据包

管线最终产物 = 交给车机 Qt 工程的数据包（车机不解析 docx）。每份手册一次运行一个目录：

```
dist/A_202608/
├── manifest.json             # 文档、变体、手册版本、schema_version、逐文件 sha256、规模计数
├── tree_A.json               # 本手册文档树（章节 + 内容块）
├── fault_codes.json          # 本手册抽得的故障码
├── maintenance_rules.json    # 本手册抽得的保养规则
├── audit.json                # 审核清单（E）
└── img/                      # 本手册全部插图，PNG/JPEG、按 800px 宽转码
```

- 流转：运行目录 → 组装为变体包 → ① 拷入车机**文件系统数据目录**（不编译进 qrc——OTA 可单独更新数据不动 App；启动按 manifest 校验和验完整性）→ ② 载入 10.90.20.110 MySQL 作后端管理副本。车机第一批不连 MySQL；
- 变体组装（A/B 故障码双来源合并去重、按变体清单选拷树与规则）是独立的轻量脚本，待"手册 Tab 是否含 B"定案后编写。

### 6.2 管线（`pipeline/` 独立目录，命令行工具）

与 RAGFlow 的边界：第一批**零代码依赖**（python-docx/lxml 直解，不 import ragflow 模块）；第二批 D 语料入库走 RAGFlow 知识库 HTTP API，同样不 import 内部代码。

```bash
python pipeline.py --input 手册A.docx --doc A --variant 国内干桥 --version 202608 --out dist/
```

八个阶段，每阶段落盘中间产物、可单独重跑（版本差异报告 = 两次 DocumentModel 的 diff）：

| 阶段 | 内容 | 要点 |
|---|---|---|
| 0 校验 | 文件头校验 | docx 必须 `PK`、doc 必须 `D0 CF 11 E0`，含 E-SafeNet/LOCK 字样直接拒收；.doc 在服务器经 LibreOffice 转 .docx |
| 1 解析 | docx → DocumentModel | 段落/表格按文档流保序交错；图片以 rId 锚定段落；表格网格展开合并单元格（vMerge 续行前向填充） |
| 2 编号 | 编号注入 | A/C：标题样式大小写不敏感识别（本手册样式名为小写 "heading n"）+ 位置推导 + 目录交叉验证；B：字面编号四种格式归一（00/一、/1.2.4.1/§1.1 → 点分十进制），映射写死进黄金测试 |
| 3 表格分类 | 四类分拣 | 警告框 / 故障码表 / 保养周期表 / 排版用表（溶解成段落，进审核清单） |
| 4 图片 | 提取转码 | media 落盘并按章节命名；EMF/WMF 经 LibreOffice 转 PNG；按 800px 宽转码；断言零孤儿 |
| 5 产品切分 | tree / B1 / C | 树切分与六种块规整；B1 表头映射 + 同码多等级行折叠取最高（进审核）+ 空措施打待审标；C 周期表逐 ● 成规则、累积/首保短语确定性解析，匹配不上进审核清单不猜 |
| 6 打包 | manifest | 逐文件 sha256 + 规模计数 |
| 7 审核 | 审核清单（E） | 全阶段副产物汇总 → audit.json |

例外：A 3.2 润滑周期为图示，管线提图 + 生成空模板 CSV 人工填写，不上 OCR。

## 附录 B：工程注意事项

### B.1 文档加密（DRM）防线 ⚠️

本机装有亿赛通（E-SafeNet）企业文档加密：**Word 保存的文件会被透明加密**，仅授权进程可读；Python/RAGFlow 读到的是密文（文件头含 `E-SafeNet…LOCK` 字样），**解析静默产出垃圾内容**。

对策：

1. 入库/入管线前**校验文件头**：docx 必须 `PK` 开头、doc 必须 `D0 CF 11 E0` 开头，异常直接告警拒收；
2. 当前三份源文件均为明文，但**任何"Word 另存为"产物都是密文**——不要用本机 Word 做格式转换；
3. .doc 转换路径：在无 DRM 的服务器上用 LibreOffice 转，或走 Word COM **内存提取**（打开→读内容→由非受控进程写盘），不要落盘 SaveAs。

### B.2 RAGFlow 相关（v0.27.3 代码实测）

| 事项 | 结论 | 位置 |
|---|---|---|
| manual 分块器样式判断 | 大小写敏感 `startswith("Heading")`，本三份手册样式名为小写 "heading N"，**直接入库识别不到任何标题** | `rag/nlp/__init__.py:1769` |
| Word 自动编号 | 全仓库无 `w:numPr` 解析，正文文字里没有编号 → **必须预处理注入编号** | `deepdoc/parser/docx_parser.py` |
| .doc 支持 | manual 分块器对 .doc 直接 `NotImplementedError` → 必须转换 | `rag/app/manual.py:306` |
| parent-child 检索 | naive 分块器支持（`children_delimiter` → 母块/子块检索），可用于"总-分"式回答 | `rag/app/naive.py:1137`、`rag/nlp/search.py:1101` |
| GraphRAG | 默认实体类型（organization/person/geo/event/category）与故障域不匹配 → **故障表不要走 GraphRAG，确定性解析** | `rag/graphrag/general/extractor.py:46` |
| Agent 组件 | 问答/诊断画布所需组件齐备：Categorize/Switch/Message/UserFillUp/Retrieval/Invoke/ExeSQL | `agent/component/` |

### B.3 变体元数据

所有数据产品统一携带：市场（国内/EU）、配置（干桥/湿桥、电液比例）、受众（操作员/技师）、适用 SN、手册版本日期。检索/渲染/规则执行均按变体过滤，防止配置串线（如湿桥驱动桥油要求答给干桥用户）。

### B.4 引用规范

A 与 C 编号体系不同（启动前检查：A=2.5.1，C=4.8.3），对外引用一律带文档标识（"A 手册 2.5.1"），`section_id` 编码已内置文档代号。

# DOCX 原始元素解析与语义转换

## 1. 文档目的与范围

本文说明 XC975 随车手册流水线如何从 DOCX 中提取原始元素，以及这些原始元素如何经过确定性规则转换为章节、正文、图片、表格、警告、步骤和列表等语义元素。

本文讨论的是 `pipeline/xc975_pipeline/` 下的随车手册流水线，不是 RAGFlow 通用知识库中的其他 DOCX 解析路径。

整个转换不依赖大模型自由理解文档，主要使用：

- `python-docx`：读取 DOCX 文档、段落、表格和图片部件。
- XML 节点遍历：处理内容控件、行内对象、图片关系等结构。
- 样式识别：识别标题和目录。
- 正则表达式：识别章节编号、图注、列表和步骤。
- 表格分类规则：区分警告框、故障码表、周期表、排版表和普通数据表。
- 状态化遍历：建立章节树，并聚合连续列表和连续步骤。

主要代码位置：

| 功能 | 代码 |
|---|---|
| 原始元素解析 | `pipeline/xc975_pipeline/docmodel.py` |
| 标题、编号和目录 | `pipeline/xc975_pipeline/numbering.py` |
| 图片提取与转码 | `pipeline/xc975_pipeline/images.py` |
| 表格分类 | `pipeline/xc975_pipeline/tables.py` |
| 章节树和语义块生成 | `pipeline/xc975_pipeline/products/tree.py` |
| 语义数据结构 | `pipeline/xc975_pipeline/schemas.py` |
| 整体调度 | `pipeline/xc975_pipeline/runner.py` |

## 2. 整体处理流程

```text
DOCX 原始文档
    │
    │ parse_docx()
    ▼
保序的原始元素流 list[Element]
    ├─ 段落 Element(kind="para")
    └─ 表格 Element(kind="table")
    │
    ├─ 标题识别与编号注入
    ├─ 目录提取与交叉验证
    ├─ 图片关系解析与图片落盘
    ├─ 表格分类
    │
    │ build_tree()
    ▼
语义章节树 list[Section]
    └─ blocks
       ├─ para     普通正文或图文混排
       ├─ image    图片及题注
       ├─ table    表格
       ├─ warning  警告
       ├─ steps    操作步骤
       └─ list     项目列表
```

原始解析和语义转换分别回答两个问题：

- 原始解析：DOCX 中有什么，出现顺序是什么？
- 语义转换：这些内容在手册中承担什么作用，应当如何组织？

## 3. 从 DOCX 中直接解析出的原始元素

### 3.1 统一的原始元素模型

正文中的段落和表格被转换为统一的 `Element`，并按文档流顺序交错排列：

```python
Element(
    kind="para" 或 "table",
    index=原始文档流位置,
    para=段落数据或 None,
    table=表格数据或 None,
)
```

`index` 是原始元素 ID。后续章节、内容块、故障码和保养规则通过 `src` 保存这些 ID，从而反查原始来源。

图片和文本框不是独立的顶层 `Element`：图片锚定在段落或表格单元格中，文本框以其锚定段落的 `text_boxes` 列表保存。

### 3.2 段落 `para`

每个正文段落可以解析出以下信息：

| 字段 | 含义 |
|---|---|
| `text` | 段落全文，不包含文本框文字 |
| `style` | Word 段落样式名，例如 `heading 1`、`Heading 2`、`toc 1` |
| `image_rids` | 段落中全部图片的关系 ID 列表 |
| `text_boxes` | 锚定在该段落上的文本框文字列表，每个文本框独立保存 |
| `has_num_pr` | 是否具有 Word 自动编号属性 `w:numPr` |
| `parts` | 段落内部按顺序排列的文本片段和图片片段 |
| `index` | 该段落在原始文档流中的元素 ID |

其中，`has_num_pr` 当前只用于帮助识别步骤，不会还原 Word 自动编号的具体数字。

#### 段落内部片段 `parts`

`parts` 用于保留行内图文顺序。例如：

```text
“本手册中的” + [行内图片] + “符号表示安全预防措施”
```

可表示为：

```json
[
  {"kind": "text", "text": "本手册中的"},
  {"kind": "image", "rid": "rId8"},
  {"kind": "text", "text": "符号表示安全预防措施"}
]
```

这样，后续转换不需要把行内图片统一移动到段落末尾。

#### 文本框 `text_boxes`

支持 DrawingML 和旧版 VML 文本框。每个文本框单独提取，不与锚定段落正文拼接；框内多个段落使用换行连接，框内表格的单元格文字也会读取。

对于 `mc:AlternateContent`，当 `mc:Choice` 已包含同一文本框时，会跳过 `mc:Fallback` 中的重复副本；只存在于 Fallback 中的文本框仍然保留。嵌套文本框分别提取，外层不会重复包含内层文字。

### 3.3 段落中的文本结构

当前能够读取或保留以下文本内容：

- 普通文字节点 `w:t`。
- 制表符 `w:tab`，在内部片段中转换为 `\t`。
- 手动换行 `w:br` 和回车换行 `w:cr`，在内部片段中转换为 `\n`。
- 超链接容器中的显示文字。
- `smartTag` 容器中的文字。
- 修订标记 `w:ins` 中的插入文字。
- 简单域 `w:fldSimple` 的结果文字。
- `customXml` 容器中的文字。
- 行内容控件 `w:sdt`、`w:sdtContent` 中的文字。

超链接只保留显示文字，不保留 URL。复杂域的域代码和域参数不作为独立数据保存。

### 3.4 表格 `table`

表格被解析为展开后的逻辑二维网格：

| 字段 | 含义 |
|---|---|
| `grid` | 单元格文本网格 |
| `cell_rids` | 与文本网格对应的单元格图片关系 ID 网格 |
| `col_spans` | 每个逻辑单元格的跨列信息 |
| `row_spans` | 每个逻辑单元格的跨行信息 |
| `index` | 表格在原始文档流中的元素 ID |

具体处理包括：

- 展开 `gridSpan` 横向合并单元格。
- 处理 `vMerge` 纵向合并单元格。
- 对纵向合并的续接单元格进行文本前向填充。
- 记录真实跨行数；续接位置的 `row_spans` 为 `0`。
- 单元格中的多个普通段落使用换行连接。
- 将嵌套表格文本展平到父单元格，嵌套表格的一行使用 ` | ` 连接各单元格。
- 扫描单元格及其后代节点中的图片关系。

嵌套表格不会生成独立的顶层表格元素。

### 3.5 图片及图片锚点

支持两种图片关系：

- DrawingML：`a:blip@r:embed`。
- VML：`v:imagedata@r:id`，主要用于兼容由旧版 `.doc` 转换的文档。

可以发现的图片位置包括：

- 正文段落中的独立图片。
- 正文段落中的行内图片。
- 表格单元格中的图片。
- 排版表格中的图片。
- `w:drawing`、`w:pict`、`w:object` 中可找到的图片或预览图。

图片提取后生成：

- 实际图片文件。
- `rId → 文件名` 映射。
- 表格单元格到图片文件的对应网格。
- 行内图文混排所需的图片片段。

图片处理规则包括：

- 按所属章节命名，例如 `A_2_5_1_01.png`。
- 首个标题之前的图片使用 `front` 作为章节名。
- 同一媒体部件被多处引用时只落盘一次。
- 默认把宽度超过 800px 的图片等比缩小至 800px。
- EMF、WMF 优先通过 LibreOffice 转为 PNG。
- 矢量图无法转换时保留原文件并写入审核清单。
- 图片关系没有对应媒体部件时写入审核清单。

### 3.6 内容控件和自动目录

正文块级的 `w:sdt` 会展开其 `w:sdtContent`。

因此，Word 自动目录即使被包裹在内容控件中，其中的段落仍能进入原始元素流，不会被整页跳过。

### 3.7 文档顺序

原始元素流保留正文段落与表格的相对顺序：

```text
段落 → 段落 → 表格 → 段落 → 图片所在段落 → 表格
```

不会先读取全部段落、再读取全部表格。

## 4. 原始元素如何转化为语义元素

### 4.1 第一步：识别标题并注入编号

`inject_numbers()` 遍历原始元素流，为标题段落补充：

- `heading_level`：标题层级。
- `编号`：归一化或推导后的章节编号。

这两个字段直接补充到原来的 `Element` 上，而不是复制出另一份段落。

#### 根据样式识别标题

标题样式匹配不区分大小写：

```text
heading 1 → 一级标题
Heading 2 → 二级标题
heading 3 → 三级标题
heading   → 一级标题
```

#### A/C 手册：按标题位置推导编号

程序为各标题层级维护计数器：

```text
Heading 1  操作       → 2
Heading 2  起动之前   → 2.5
Heading 3  日常检查   → 2.5.1
```

出现较高级标题时，所有更低级计数器归零。若标题层级跳跃，则生成审核项。

#### B 手册：归一化原文编号

支持的典型格式包括：

```text
00 总则       → 0
01 电气       → 1
一、故障表现  → 1
§1.1 范围     → 1.1
1.2.4.1 工序  → 1.2.4.1
1 电气系统    → 1
```

多级点分编号也用于确定标题层级，避免 Word 样式层级不足时丢失更深层级。

### 4.2 第二步：提取目录并交叉验证

样式名以 `toc` 开头的段落被识别为目录段落。

例如：

```text
2.5.1 日常检查.........57
```

会被解析为：

```python
("2.5.1", "日常检查", "57")
```

目录条目包含：

- 编号。
- 标题。
- 可选页码。

程序将目录与正文标题按标题出现顺序配对，检查：

- 目录条目是否在正文中没有对应标题。
- 目录编号是否与正文推导编号不一致。

目录主要用于校验，不直接成为最终章节树中的独立语义块。

### 4.3 第三步：将图片关系转换为实际图片文件

原始元素中只有 `rId8` 等关系 ID。`extract_images()` 根据关系 ID 找到 DOCX 内部媒体部件，完成图片落盘、转码和缩放，并返回：

```python
{
    "rId8": "A_2_5_1_01.png",
    "rId9": "A_2_5_1_02.png"
}
```

语义转换阶段通过这个映射创建图片块或图文混排片段。

### 4.4 第四步：识别表格语义

`classify_table_detailed()` 将表格分为五类：

| 分类 | 含义 | 语义转换方式 |
|---|---|---|
| `warning` | 警告框 | 转为 `WarningBlock` |
| `fault_code` | 故障码表 | 保留为 `TableBlock`，并用于故障码抽取 |
| `period` | 保养周期表 | 保留为 `TableBlock`，并用于保养规则抽取 |
| `layout` | 排版容器 | 溶解为正文块和图片块 |
| `data` | 普通数据表 | 保留为 `TableBlock` |

典型判定规则包括：

- 第一格以警告词开头且列数不超过两列：`warning`。
- 表头同时含代码列和名称列：`fault_code`。
- 位于故障码章节 `3.10...`：`fault_code`。
- 位于保养周期章节 `3.3...`：`period`。
- 单元格含 `●` 周期标记：`period`。
- 只有一行或一列：`layout`。
- 未命中专门规则：`data`。

分类结果附带判定依据，并允许人工改标。

### 4.5 第五步：通过 `build_tree()` 建立章节树

`build_tree()` 顺序遍历原始元素流，并维护两个状态：

```python
stack   = 当前章节层级栈
pending = 正在连续聚合的 list 或 steps 块
```

#### 遇到标题：创建章节

带有 `heading_level` 的段落被转换为 `Section`：

```text
section_id  章节唯一 ID
seq         章节顺序
章节号       点分章节编号
标题         标题文字
层级         标题层级
parent      父章节 ID
面包屑       从上级章节到当前章节的路径
src         标题原始元素 ID
blocks      章节正文内容
```

章节栈用于确定父子关系：

- 新标题层级更深：挂到当前章节下面。
- 新标题层级相同：结束旧章节，创建同级章节。
- 新标题层级更浅：弹出更深层章节，回到相应上级。

标题之后的普通内容进入当前章节的 `blocks`。首个标题之前的封面等内容不进入最终章节树。

#### 遇到表格：按表格分类转换

```text
warning → WarningBlock
layout  → 若干 ParaBlock 和 ImageBlock
其他    → TableBlock
```

排版表按照行、列和单元格顺序溶解；每个单元格先输出文字，再输出该单元格中的图片。

#### 遇到图片段落：创建图片或图文混排

处理规则为：

1. 段落有文字且 `parts` 中含行内图片：生成一个带 `parts` 的 `ParaBlock`。
2. 否则，每张图片生成一个 `ImageBlock`。
3. 独立图片之外如果还有段落文字，再生成一个 `ParaBlock`。

#### 题注、警示与行内格式

- 图题支持 `图2-38`、`图1.2` 等编号，绑定到前一个图片块；表题使用相同编号形式，绑定到后一个表格块。`题注` 保留完整原文，阅读界面负责避免编号重复显示。
- `图A / 图B` 这类位于多幅图片之前的分图标签按顺序绑定到后续图片。
- 位图和矢量转 PNG 后统一裁掉纯白外边框，保留 12px 安全边距；图形内部空白不受影响。
- 独立的 `★ 注意/警告/危险` 转为 `WarningBlock`；紧随其后的一组步骤收纳到该块的 `items` 中。其他星号引导的操作小标题使用 `ParaBlock.role = "subheading"`。
- 文本片段保留粗体、斜体、下划线和上下标；字体、原始字号和页面间距不进入阅读数据。
- 图片块和行内图片记录提取后文件的 `width` / `height`，供阅读页预留尺寸，避免懒加载造成章节跳动。

#### 遇到文本框：创建独立正文块

锚定段落的正文、图片和列表/步骤先按各自规则处理，随后将 `text_boxes` 中的每个文本框依次转换为独立 `ParaBlock`。即使锚定段落没有正文或图片，文本框也不会被丢弃。

文本框块的 `src` 使用锚定段落的原始元素 ID。文本框内容当前按普通正文保留，不再递归套用列表、步骤、图注或警告分类规则。

#### 识别图注

符合以下格式的段落可以作为图注：

```text
图2-38 日常检查位置
```

如果它紧跟一个尚无题注的图片块，则并入图片块：

```json
{
  "type": "image",
  "file": "A_2_5_1_01.png",
  "图号": "图2-38",
  "题注": "图2-38 日常检查位置",
  "src": [25]
}
```

否则，该段仍按普通正文处理。

#### 识别连续列表

以下符号开头的段落被识别为列表项：

```text
● ○ · ◆ ■ □ ▲ △
```

连续列表段落聚合成一个 `ListBlock`，去掉每项开头的符号：

```json
{
  "type": "list",
  "style": "check",
  "items": ["检查冷却液", "检查液压油"],
  "src": [23, 24]
}
```

#### 识别连续步骤

满足以下任一条件的段落可以识别为步骤：

- 具有 Word 自动编号 `has_num_pr=True`。
- 文本匹配 `1.`、`1、`、`1)`、`1）` 等数字前缀。
- 文本以 `①` 至 `⑩` 开头。

连续步骤聚合成一个 `StepsBlock`。对自动编号段落，目前保留原文，不额外生成自动编号文字。

#### 其他段落：转换为普通正文

未命中标题、图片、图注、列表和步骤规则的非空段落，转换为：

```json
{
  "type": "para",
  "text": "本手册适用于XC975-EV。",
  "src": [34]
}
```

### 4.6 连续块何时结束

`pending` 中正在收集的列表或步骤，在遇到以下情况时结束：

- 新标题。
- 表格。
- 图片段落。
- 另一种列表/步骤类型。
- 普通正文。
- 文档结束。

例如：

```text
● 项目一
● 项目二
普通正文
● 项目三
```

会生成：

```text
list（项目一、项目二）
para（普通正文）
list（项目三）
```

项目三不会并入第一个列表。

### 4.7 人工确认的段落合并

文档树初步生成后，可以根据工作台传入的 `merge_pairs` 合并被错误拆开的相邻正文段落。

必须同时满足：

- 用户明确确认合并。
- 两个块都是普通正文块。
- 原始元素 ID 相邻。
- 原始段落样式相同。
- 前一段没有句末标点。
- 当前段不是图、表、注释或注意事项的开头。

合并后保留拼接文本、全部 `src` 以及已有图文 `parts`。

## 5. 转换后的语义元素

### 5.1 章节 `Section`

章节是语义树的骨架：

```json
{
  "section_id": "A-2.5.1",
  "seq": 10,
  "章节号": "2.5.1",
  "标题": "日常检查",
  "层级": 3,
  "parent": "A-2.5",
  "面包屑": "2 操作 > 2.5 起动之前 > 2.5.1 日常检查",
  "src": [21],
  "blocks": []
}
```

其中：

- `src` 表示该章节的标题来自哪个原始元素。
- `blocks` 按顺序保存该章节的正文内容。

### 5.2 六种内容块

| 类型 | 主要字段 | 来源 |
|---|---|---|
| `para` | `text`、`parts`、`src` | 普通段落或行内图文段落 |
| `image` | `file`、`图号`、`题注`、`src` | 段落图片、表格图片及图注 |
| `table` | `header`、`rows`、`cell_images`、`col_spans`、`row_spans`、`src` | 数据表、故障码表、周期表 |
| `warning` | `level`、`text`、`src` | 警告表格 |
| `steps` | `items`、`src` | 连续编号段落或步骤文本 |
| `list` | `style`、`items`、`src` | 连续项目符号段落 |

所有内容块都通过 `src` 保存原始元素 ID。列表、步骤或合并正文涉及多个原始段落时，`src` 会包含多个 ID。

## 6. 完整转换示例

### 6.1 原始元素流

```text
[20] para  style=heading 2  text="起动之前"
[21] para  style=heading 3  text="日常检查"
[22] para  text="每天使用机器前检查："
[23] para  text="● 检查冷却液"
[24] para  text="● 检查液压油"
[25] para  image_rids=["rId8"]
[26] para  text="图2-38 日常检查位置"
```

### 6.2 标题编号注入

```text
[20] heading_level=2  编号="2.5"
[21] heading_level=3  编号="2.5.1"
```

### 6.3 语义转换结果

```json
{
  "section_id": "A-2.5.1",
  "章节号": "2.5.1",
  "标题": "日常检查",
  "层级": 3,
  "parent": "A-2.5",
  "src": [21],
  "blocks": [
    {
      "type": "para",
      "text": "每天使用机器前检查：",
      "src": [22]
    },
    {
      "type": "list",
      "style": "check",
      "items": ["检查冷却液", "检查液压油"],
      "src": [23, 24]
    },
    {
      "type": "image",
      "file": "A_2_5_1_01.png",
      "图号": "图2-38",
      "题注": "图2-38 日常检查位置",
      "src": [25]
    }
  ]
}
```

这个例子中发生了四种语义转换：

1. 标题样式和位置信息转换为章节及章节层级。
2. 普通段落转换为 `para`。
3. 连续项目符号段落聚合为一个 `list`。
4. 图片段落与后续图注合并为一个 `image`。

## 7. 当前能力边界

以下能力不能视为这条流水线已经支持：

- 页眉、页脚不作为正文原始元素解析。
- 脚注、尾注和批注不解析。
- 文本框的边框、位置、大小和环绕方式不保留，只提取文字。
- 数学公式不解析。
- SmartArt 和图表中的结构化数据不解析。
- OLE 对象本体不解析，只可能取得其图片预览。
- 不保留字体、字号、颜色、粗体、斜体和下划线等字符格式。
- 不保留段落对齐、缩进、行距等排版属性。
- 不保留表格边框、底纹、列宽和单元格对齐。
- 不保留超链接 URL、书签和交叉引用目标。
- 不保留正文真实分页坐标；目录页码只是目录文本的解析结果。
- 不含图片或文本框的空段落会进入原始元素流，但生成章节树时会被丢弃。
- 首个标题之前的内容会进入原始元素流，但不会进入最终章节树。

## 8. 总结

从原始 DOCX 到语义文档树，可以概括为：

```text
parse_docx()
  负责读取段落、表格、图片锚点及其顺序

inject_numbers()
  负责标题识别、层级判断和章节编号

extract_toc() + cross_check_toc()
  负责目录提取和正文一致性校验

extract_images()
  负责把图片关系 ID 转换为实际图片文件

classify_table()
  负责判断表格的用途

build_tree()
  负责建立章节层级，并把段落、表格和图片转换为六类语义内容块
```

最终得到的不再只是一个文本列表，而是具有章节层级、内容类型、图片文件、表格结构和原始来源锚点的语义文档树。
